# Phase 4 — UI Design Contract: Backup robusto + contenido completo

> Visual and interaction contract for the new `backup` screen, the home backup-reminder banner, and the extended home action row. Generated by `gsd-ui-researcher` after locking with CONTEXT (D-73..D-88) and RESEARCH (Patterns 1-5, Code Examples §1-3).

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Pico CSS classless, no design-token system) |
| Preset | not applicable |
| Component library | Pico CSS 2.1.1 (CDN, SRI pinned in `index.html`) |
| Icon library | None — Unicode glyphs only (`⚠`, `←`, `●`, `✓`, `★`, superíndices `¹²³ᵃᵇᶜ`) |
| Font | Pico defaults (system stack); no custom font declared in Phase 1-3 |
| State framework | Alpine.js 3.15.12 (CDN, SRI pinned) |

**No shadcn** — project is vanilla HTML + Alpine + Pico classless. The shadcn initialization gate is N/A (rejected at project start, locked in CLAUDE.md tech stack). Registry safety gate: N/A.

**Established visual coherence anchors (do not reinvent):**
- `<template x-if="currentScreen === '...'">` switch over `currentScreen` (4 → 5 screens after this phase). Pattern D-24/D-25/D-84.
- `<article>` is the outer container for every screen. `<header>` carries the screen title.
- `.button-row` class is the canonical wrapper for any pair/triple of adjacent buttons (NOT Pico's `role="group"`, which glues borders).
- `.inflight-banner` (Phase 2) is the visual template for any persistent home-level alert — reused by extension for `.backup-banner`.
- `.confirm-inline` (Phase 2 D-27, used by D-43/D-44) is the canonical inline confirmation modal — reused as-is for D-76 (4th call-site).
- Spanish UI strings, ASCII slugs/IDs, no decorative emojis (only the `⚠` glyph in alert banners is acceptable per the established Phase 2 tone).
- All buttons that take the user home use the wording `← Volver al home` (lowercase verb, lowercase noun). Established Phase 2 (picker, summary).

## Spacing Scale

Inherited 1:1 from Pico CSS defaults + Phase 1-3 conventions. **Do not declare new tokens.** All spacing comes from Pico's CSS variables (`--pico-spacing`) or explicit rem multiples of `0.25rem` (=4px at default 16px root).

| Token (rem) | Pixels | Phase 4 Usage |
|-------------|--------|---------------|
| 0.25rem | 4px | (n/a — finer than this is unused) |
| 0.5rem | 8px | Gaps inside `.backup-banner` button row, inline padding |
| 0.75rem | 12px | Vertical padding inside `.backup-banner` and the inflight banner (already used) |
| 1rem | 16px | Default `.button-row` gap, banner horizontal padding, status-line vertical margin |
| 1.5rem | 24px | `.button-row` vertical margin (existing), space between backup screen sections |
| 2rem+ | 32px+ | Section breaks within the backup screen (Pico's `<article>` padding handles this) |

**Exceptions:** None for Phase 4. The backup screen does not introduce any spacing value outside what Phase 2/3 already use. The banner reuses the exact same `0.75rem 1rem` padding + `1rem` `margin-bottom` as `.inflight-banner` for visual coherence.

## Color

Phase 4 introduces **zero new color tokens.** All colors come from Pico CSS variables (with hex fallbacks already in `styles.css`) and the 60/30/10 system already established Phase 2.

| Role | Value | Phase 4 Usage |
|------|-------|---------------|
| Dominant (60%) | `--pico-background-color` (light: white; dark: near-black auto via `color-scheme`) | App canvas, backup screen `<article>` background, message-area neutral state |
| Secondary (30%) | `--pico-card-background-color` + `--pico-muted-border-color` (#e0e0e0) | Card borders, dashed/solid borders inside the screen, `<hr>` separators |
| Accent (10%) — primary | `--pico-primary` (#1095c1 Pico cyan) | Default `<button>` background (used for: "Exportar progreso", "Continuar" in confirm) — Pico applies it implicitly |
| Accent (10%) — secondary muted | `--pico-secondary` via `class="secondary"` | Buttons that should NOT compete for attention: "Backup" (home), "Importar progreso", "Cancelar" (confirm), "← Volver al home" |
| Warning (banner only) | `--pico-color-amber-500` (#f59e0b) border + `rgba(245, 158, 11, 0.08)` background | `.backup-banner` border + tint, exactly mirroring `.inflight-banner` Phase 2 |
| Destructive feedback | `--pico-color-red-500` (#d32f2f) | Error text in the message area when import/export fails; the `⚠` glyph inside the banner inherits banner text color (NOT red — amber-tinted background carries the warning, not the icon) |
| Success feedback | `--pico-color-green-500` (#2e7d32) | Success text in the message area after successful export/import |

### Accent reserved for (explicit list)

The **default Pico `<button>` accent (cyan primary)** is used in Phase 4 ONLY for these elements:
1. `Exportar progreso` button on the backup screen (primary action of the screen).
2. `Continuar` button inside the import confirmation modal (`.confirm-inline`).

Every other button uses Pico's `class="secondary"`:
- `Backup` button on the home (per D-81 — "no compite con los protagonistas Repaso/Test completo").
- `Importar progreso` button on the backup screen.
- `Cancelar` button inside the import confirmation modal.
- `← Volver al home` button at the bottom of the backup screen.
- `Ir a Backup` button inside the home banner.

### Destructive action color decision

The import operation is destructive (REPLACES state irreversibly). **CONTEXT D-76 originally noted "primario rojo destructivo"**, but Phase 2 established the precedent that `requestConfirm()` uses Pico's default primary button (cyan) without a red variant — UAT 02-04 accepted this for the "Descartar in-flight test" confirmation, which is also destructive. **Resolution:** Use Pico's default primary (cyan) for `Continuar`, NOT a red variant. The destructive nature is communicated by the **copy** ("Esto REEMPLAZARÁ tu progreso actual y no se puede deshacer") rendered as plain `<p>` body text — NOT by color. This preserves visual coherence with the 3 prior confirmation call-sites. If UAT explicitly requests red here, add `.confirm-destructive` class as a Phase-4 follow-up; do NOT branch the helper preemptively.

### Banner glyph color

The `⚠` glyph in `.backup-banner` and `.inflight-banner` inherits the surrounding text color (default Pico text). The amber tint comes from the **border + background**, not the glyph. This matches the Phase 2 visual treatment.

### Message-area color encoding (`backupLastMessage`)

```
backupLastMessage.kind === 'success'  → text in green (--pico-color-green-500)
backupLastMessage.kind === 'error'    → text in red   (--pico-color-red-500)
backupLastMessage === null            → element not rendered (NO empty box)
```

These two colors are already in `styles.css` (`button.correcta` / `button.incorrecta` / `.delta-promotion` / `.delta-regression`). No new color declarations.

## Copywriting Contract

All copy is in **Spanish (Castilian)**, lowercase verbs unless start-of-sentence, no decorative emojis except `⚠` (warning) and `←` (back arrow). Strings are hardcoded in `index.html` and `src/screens/app.js` per FOUND-04 (no i18n in v1).

### Home banner copy (per D-80)

The banner appears above the `.button-row.button-row-prominent` and below `.inflight-banner` (if both are visible). Two variants computed by getter `backupBannerText`:

| Condition | Banner body | Action |
|-----------|------------|--------|
| `state.lastBackupAt === null` and `daysSince(firstUsedAt) > 7` | `⚠ Aún no has exportado tu progreso.` | `<button class="secondary" @click="currentScreen = 'backup'">Ir a Backup</button>` |
| `state.lastBackupAt !== null` and `daysSince(lastBackupAt) > 7` | `⚠ Han pasado <N> días desde tu último backup.` (where `<N>` is `daysSinceISO(lastBackupAt, todayLocal())`, plain integer) | Same `Ir a Backup` button |

**Special-cases:**
- `N === 1` → still render "1 días" (no special pluralization — coherent with `streakLabel` Phase 2 which uses "1 / 21 d" without distinguishing singular). If UAT calls this out, fix as a Phase-4 polish — do NOT block the contract on it.
- `daysSinceISO < 0` (clock skew / future-dated): banner hidden by the getter (Pitfall #5 in RESEARCH). Do NOT show negative days.

**Banner does NOT include a snooze/dismiss control** (D-80). Period. No "Más tarde", no "X" close icon. The only escape is to actually export.

### Home action row — third button (per D-81)

Extend the existing `.button-row.button-row-prominent` from 2 buttons to 3:

| Button | Class | Label | Handler |
|--------|-------|-------|---------|
| Primary 1 | (default) | `Repaso 20` | `openPicker('repaso')` (unchanged) |
| Primary 2 | (default) | `Test completo` | `openPicker('test-completo')` (unchanged) |
| Secondary | `secondary` | `Backup` | `currentScreen = 'backup'` |

The three buttons share the row via `flex: 1` — they will each occupy ~33% width on desktop. The visual hierarchy comes from the `secondary` class (lower contrast), not from size or position. Layout-wise the `Backup` button sits **to the right** of `Test completo`. Rationale: maintains reading order primary→primary→secondary; the secondary button visually de-emphasizes itself naturally.

### Status line copy

| Condition | Copy |
|-----------|------|
| `state.lastBackupAt === null` | `Aún no has exportado tu progreso.` (plain `<p>`, muted color via `class="picker-warning"`) |
| `state.lastBackupAt !== null` | `Último backup: <fecha local legible> (hace <N> días).` |

**Fecha local legible format:** `new Date(state.lastBackupAt).toLocaleDateString('es-ES', { day: 'numeric', month: 'long', year: 'numeric' })` → e.g. `24 de mayo de 2026`. The "hace N días" suffix uses the same `daysSinceISO` helper as the banner. When `N === 0`, render `(hoy)` instead of `(hace 0 días)`. When `N < 0` (clock skew), render `(fecha futura)` — does not crash the screen.

### Message area copy (`backupLastMessage`)

Rendered as a single `<p>` (or `<div>` if multi-line in the future) below the button row. Element is **only rendered when `backupLastMessage !== null`** — there is no empty placeholder box.

| Kind | When | Copy template |
|------|------|---------------|
| success (export) | After `exportBackup()` finishes successfully | `Progreso exportado. Guarda el archivo en lugar seguro.` |
| success (import) | After `commitImport()` finishes | `Progreso importado correctamente.` |
| error (read fail) | `Blob.text()` throws | `No se pudo leer el archivo: <error message>` |
| error (parse fail — no JSON) | `JSON.parse` throws inside `parseBackupFile` | `JSON inválido: <error message>` |
| error (parse fail — wrong kind) | `wrapper.kind !== 'italian-course-backup'` | `Este archivo no es un backup de Italian Course (falta o difiere el campo "kind").` |
| error (parse fail — missing state) | `wrapper.state` absent or not object | `El archivo no contiene el campo "state" o no es un objeto.` |
| error (parse fail — missing schemaVersion) | `state.schemaVersion` absent / non-number | `El campo "state.schemaVersion" falta o no es número.` |
| error (parse fail — schema mismatch) | `wrapper.schemaVersion !== state.schemaVersion` | `Versión inconsistente en el archivo (wrapper.schemaVersion=<X>, state.schemaVersion=<Y>).` |
| error (parse fail — future version) | `state.schemaVersion > 3` | `Este backup viene de una versión más nueva de la app (schemaVersion=<X>; esta app soporta hasta 3).` |
| error (export crash) | Any throw inside `exportBackup()` | `Error al exportar: <error message>` |

**Message persistence:** `backupLastMessage` is set in-memory only (not persisted to localStorage). It is **cleared automatically** when the user leaves the backup screen (set to `null` in the transition `currentScreen = 'home'`). It is NOT cleared on a successful subsequent action — instead the message gets overwritten by the new outcome. This matches the natural mental model "the last thing I tried".

### Import confirmation dialog body (per D-76)

Reuses the `.confirm-inline` panel exactly as Phase 2 implemented it. The `confirmDialog.message` string is multi-line (newlines render as `\n` because the panel uses `<p x-text>` which preserves them via `white-space: pre-line` style — see Implementation Notes below).

Exact template (string-interpolated by `buildImportConfirmMessage(summary)`):

```
Vas a importar un backup del <fecha local del exportedAt>.

Categorías con progreso: <summary.categories>
Ejercicios con stats: <summary.exercises>

Esto REEMPLAZARÁ tu progreso actual y no se puede deshacer.
```

- Fecha local del exportedAt: `new Date(summary.exportedAt).toLocaleString('es-ES')` → e.g. `24/5/2026 14:32:11`. If `summary.exportedAt === 'desconocido'` (missing field in wrapper), render literally `un backup de fecha desconocida`.
- Whitespace between paragraphs (`\n\n`) renders as a visual gap when the panel CSS includes `white-space: pre-line` on the `#confirm-message` element.

| Button | Class | Label |
|--------|-------|-------|
| Confirm | (default — Pico primary) | `Continuar` |
| Cancel | `secondary` | `Cancelar` |

These labels match the existing 3 confirmation call-sites (D-27, D-43, D-44) for consistency.

### Empty / first-use copy

- **First boot (no sessions completed):** Home shows the table (with all categories as `no-hecha`, race counter `0 / 21 d`, etc.). NO backup banner. `firstUsedAt === null` blocks the banner per D-78 logic.
- **First entry into the backup screen ever:** Status line reads `Aún no has exportado tu progreso.`. Both buttons enabled. No message area. No prior state. The screen is functional from second 1.

### Destructive confirmation (per D-76 / D-83)

The import operation is the only destructive action introduced by Phase 4. Confirmed by `requestConfirm()` inline (D-76, 4th call-site). The export operation is NOT destructive — no confirmation. Returning to home discards `backupLastMessage` and `backupPendingImport` silently (no warning) — this is desired, not a regression.

**Cancel-clears-pending-import note:** When the user cancels the confirmation, `backupPendingImport` is set back to `null` (NOT preserved). Rationale: if the user wants to retry, they can re-select the file (the input has been reset). Preserving `backupPendingImport` after cancel risks stale-state confusion — the user expects "Cancelar" to mean "fully back out".

**No "processing" intermediate state:** `Blob.text()` resolves for a 50KB–500KB JSON in single-digit ms on any modern machine. No spinner, no `isImporting` flag. If UAT discovers perceptible delay for a large transcribed-content state, add a guard then — do not preempt.

## Keyboard / Focus / Accessibility

## Implementation Notes for the planner

### File-input UX decision

**The `<input type="file">` is hidden (`display: none`) and triggered programmatically** by the `Importar progreso` button via `$refs.backupFileInput.click()`. Rationale:
- Pico's native styling of `<input type="file">` is functional but visually inconsistent with the rest of Phase 1-3 (a "Choose File" affordance with the unstyled native button is conspicuously different from Pico buttons).
- The user clicks a normal Pico `<button class="secondary">Importar progreso</button>` which calls `$refs.backupFileInput.click()` — this is the standard pattern endorsed by MDN and is accessible (the button itself is the labeled trigger).
- Layer: keep the `<input>` inside the screen's `<article>` so its lifecycle is tied to the template; ref name `backupFileInput` matches the CONTEXT D-84 sub-state `backupFileInputRef` (Alpine `$refs`).

Code shape (markup only; planner places exact code):

```html
<input type="file"
       x-ref="backupFileInput"
       accept=".json,application/json"
       @change="onFileSelected($event)"
       style="display: none">
<button type="button" class="secondary" @click="$refs.backupFileInput.click()">
  Importar progreso
</button>
```

### Banner placement order (vertical)

Inside `<template x-if="currentScreen === 'home'">`, the children are rendered in this exact order:

1. `<template x-if="inFlightTestActive">` → `.inflight-banner` (Phase 2)
2. `<template x-if="shouldShowBackupBanner">` → `.backup-banner` (new)
3. `<div class="button-row button-row-prominent">` → 3 buttons (Repaso 20 / Test completo / Backup)
4. `<figure><table>` → tabla densa

The `figure`/`table` keep their existing structure unchanged.

### Message area markup template

```html
<p x-show="backupLastMessage"
   :class="backupLastMessage?.kind === 'success' ? 'backup-message-success' : 'backup-message-error'"
   x-text="backupLastMessage?.text"></p>
```

Use `x-show` not `<template x-if>` because the contents are simple (no nested bindings) and the element is small.

### Computed values the planner must wire

- `shouldShowBackupBanner` (getter on `appShell`) — `false` if `!state`, otherwise per D-78 logic.
- `backupBannerText` (getter on `appShell`) — returns the formatted banner sentence per the "Home banner copy" table.
- `backupStatusLine` (getter on `appShell`) — returns the formatted status line per the "Status line copy" table. Single getter so the markup binding stays `<p class="picker-warning" x-text="backupStatusLine"></p>`.
- `buildImportConfirmMessage(summary)` (method) — returns the multi-paragraph string per the "Import confirmation dialog body" section.

These four computed entry points keep the markup declarative — no conditional ternaries inside `index.html`.

### Things deliberately NOT in Phase 4 visual scope

- Drag-and-drop for the file input (deferred — `<input type="file">` is sufficient).
- Progress indicator during import / export (deferred — operations complete in single-digit ms).
- Pre-export confirmation when significant time has passed (deferred — export is non-destructive).
- Snooze/dismiss control for the banner (deferred — D-80).
- Animations or transitions on banner appearance/disappearance (deferred — coherent with Phase 2/3 sobriety).
- Red destructive coloring on the `Continuar` button (deferred — Phase 2 set the precedent of cyan-primary for all confirmations).
