# Quick Task 260728-8pg: lockfile de exclusión mutua en los scripts de validación

## Objetivo

Los tres scripts de pase (`validate-ai-pass.mjs`, `validate-song-pass.mjs`,
`validate-decoy-pass.mjs`) hacen read-modify-write del archivo JSON entero sin
exclusión mutua. Con varios pases en paralelo sobre frases del MISMO archivo
(caso real de `it-add-song`: decenas de frases en un único `content/songs/*.json`,
y `validate-decoy-pass` escribe en los mismos archivos que `validate-song-pass`)
el último en escribir pisa el pase del otro (lost update) o deja el JSON corrupto.

Este plan añade un módulo compartido `scripts/lib/file-lock.mjs` con
`withFileLock(file, fn)` y lo cablea en los tres scripts, envolviendo la región
crítica completa.

**Purpose:** hoy el skill `it-add-song` documenta "NO lanzar dos loops a la vez
(corromperían el JSON)" como disciplina humana. Este cambio lo convierte en una
garantía del código, y desbloquea paralelizar los pases en el futuro.

**Output:** módulo de lock + 3 scripts cableados + tests + `.gitignore`.

**Fuera de alcance:** no se reescribe la lógica de `writePass` ni el formato de
serialización; no se toca quórum ni `deriveStatus`. La única reubicación de código
permitida es mover la LECTURA del JSON dentro del lock en `validate-decoy-pass.mjs`
(sin ella el lock no protege nada en ese script — ver Task 2).

Crear `scripts/lib/file-lock.mjs`, módulo ESM zero-deps (solo `node:fs`, `node:os`,
`node:path`, `node:process` — no añadir package.json ni dependencias, T-16-SC).

API exportada:
- `withFileLock(file, fn, opts = {})` → `async`, devuelve lo que devuelva `fn` (soporta `fn` síncrona o `async`; usar `await fn()`). Libera el lock en `finally`, pase lo que pase.
- `lockPathFor(file)` → `file + '.lock'`.
- `isProcessAlive(pid)` → `process.kill(pid, 0)` dentro de try/catch: `ESRCH` significa muerto; `EPERM` significa vivo pero de otro usuario (tratar como VIVO — nunca reclamar su lock).
- Constantes por defecto exportadas: `DEFAULT_TIMEOUT_MS = 30000`, `DEFAULT_STALE_MS = 60000`.

`opts` acepta `{ timeoutMs, staleMs, retryMinMs, retryMaxMs }` (backoff por defecto:
25ms inicial, factor 1.7, tope 500ms, jitter aleatorio de ±25%). Los overrides existen
sobre todo para que los tests corran rápido.

Adquisición:
1. `fs.openSync(lockPath, 'wx')` — atómico en POSIX y en Windows; falla con `EEXIST` si ya existe. No usar `existsSync` + `writeFileSync` (deja ventana TOCTOU).
2. Con el fd obtenido: `fs.writeSync(fd, JSON.stringify({ pid: process.pid, hostname: os.hostname(), acquiredAt: new Date().toISOString() }))` y `fs.closeSync(fd)`.
3. Si `EEXIST`: leer y parsear el lockfile. Es reclamable si (i) no parsea o le falta `pid`, (ii) `isProcessAlive(pid)` es falso, o (iii) `Date.now() - Date.parse(acquiredAt) > staleMs`. Antes de borrar, RE-LEER el lockfile y confirmar que el contenido sigue siendo el mismo (`pid` + `acquiredAt` idénticos): si cambió, otro proceso ya lo reclamó → seguir en el bucle sin borrar. Si sigue igual, `fs.unlinkSync` (tolerar `ENOENT`) y reintentar el paso 1 inmediatamente. Nunca borrar un lock de proceso vivo y reciente.
4. Si no es reclamable: esperar el backoff con jitter (`await new Promise(r => setTimeout(r, delay))`) y volver al paso 1, hasta agotar `timeoutMs`.
5. Al agotarse, lanzar un `Error` cuyo mensaje incluya la ruta del archivo, la ruta del lockfile, el `timeoutMs`, y el `pid`+`hostname`+`acquiredAt` del dueño (o el texto "propietario desconocido" si el lockfile no era legible), más la pista de borrar el `.lock` a mano si el proceso ya no existe. Mensaje en español, coherente con el resto de los scripts.

Liberación:
- `release()`: leer el lockfile y borrarlo SOLO si su `pid` es el nuestro (evita borrar el lock que otro proceso adquirió tras una reclamación). Tolerar `ENOENT`.
- Registro de handlers de proceso: mantener un `Set` a nivel de módulo con los lockfiles que este proceso tiene tomados. Instalar los handlers de forma perezosa en la PRIMERA adquisición y RETIRARLOS (`process.off`) cuando el `Set` se vacíe — así, en una corrida normal sin concurrencia, los handlers solo existen durante los pocos ms de la escritura y no alteran el comportamiento observable de los scripts.
- Handlers: `exit` → liberar de forma síncrona sin tocar el exit code (cubre también la salida por excepción/rechazo no capturado). `SIGINT` → liberar y `process.exit(130)`. `SIGTERM` → liberar y `process.exit(143)`. `uncaughtException` → liberar, imprimir `err?.stack ?? String(err)` en stderr y `process.exit(1)` (replica el comportamiento por defecto de Node para no cambiar códigos de salida).

Cablear `scripts/validate-ai-pass.mjs`:
